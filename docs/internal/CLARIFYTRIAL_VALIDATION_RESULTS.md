# ClarifyTrial 검증 결과

마지막 갱신: 2026-08-24

## 1. 현재 결론

지금까지 확인한 결과는 다음과 같다.

1. **관련 시험을 찾아오는 검색은 TrialGPT 공개 결과와 거의 같았다.** 수만 건 중
   전문가가 환자와 관련 있다고 표시한 시험을 검색 결과 상위 500개 안에 남긴 비율은
   공개 평가자료 두 개에서 83.59%,
   81.55%였다. 두 해 모두 TrialGPT 논문에 실린 수치와 소수점 첫째 자리까지
   같았다. 따라서 현재 검색 단계가 TrialGPT보다 뚜렷하게 약하다고 보기는 어렵다.
2. **답 이름을 그대로 채점하면 TrialGPT보다 낮지만, 이 차이를 실제 추천 성능
   차이로 보지 않는다.** 지시문을 만들 때 사용하지 않은 환자 33명·조건 654개에서
   현재 조건 판정 지시문은 79.1%, TrialGPT 공개 답은 88.8%였다. 그러나 별도 개발 실험에서
   틀린 51개 중 47개는 `판단 가능`과 `정보 부족` 중 어느 답을 붙일지의 차이였다.
   둘 다 후보 유지로 처리하면 조건 211개 중 207개인 98.1%가 전문가와 같았다.
   이 범위에서는 거의 모두 맞춘 셈이다. 답을 어떻게 묶느냐에 따라 통계가 크게
   달라지므로 TrialGPT의 답 이름만 따라가는 조정은 하지 않았다. 98.1%는 개발
   표본의 사후 계산이며 최종 성능으로 쓰지 않는다.
3. **모델을 여러 역할로 나눈 것만으로는 조건 판단이 좋아지지 않았다.** 같은 개발
   자료에서 한 모델이 판단한 방식은 68.7%, 역할을 나눈 두 방식은 65.9%, 65.4%였다.
   그래서 매번 검토 모델을 부르는 구조는 사용하지 않는다.
4. **부족한 정보를 묻는 순서는 개선됐다.** 새 합성 환자 30명에게 확인 기회 세 번을
   줬을 때, 모든 환자 정보를 알 때와 같은 판단에 도달한 시험은 입력 목록 순서대로
   확인한 경우 75%, 가장 많은 시험 판단을 끝낼 정보를 매번 계산한 경우 89%였다.
5. **환자가 이용하기 어려운 확인 방법을 피하도록 만들었다.** 이동·비용 부담을 넣은
   합성 상황 80회에서 실제로 이용할 수 있는 방법만 써서 판단을 끝낸 시험은 고정
   같은 비용표를 모든 환자에게 적용한 경우 81.0%, 환자의 이동·비용·시간 제한을
   반영한 경우 88.5%였다. 어려운 새 검사나 추가 방문을 제안한 횟수는
   65회에서 0회로 줄었다.

앞의 두 항목은 공개 TrialGPT 자료를 사용한 조건 판단과 검색 결과다. 뒤의 두 항목은
공개 시험 조건과 연구진이 만든 합성 환자를 사용한 초기 평가다. 서로 다른 시험이므로
하나의 총점으로 합치지 않는다. 실제 환자 자료를 사용한 평가는 하지 않았다.

## 2. 개발용 자료와 평가용 자료를 나눈 방법

공개 원본 1,015행을 환자-시험 단위로 묶었다. 조건 원문이 비어 있는 행을 포함한
조합 하나는 모델 실행에서 제외했다.

| 구분 | 환자-시험 조합 | 환자 | 조건 | 용도 |
|---|---:|---:|---:|---|
| 개발용 | 20 | 20 | 211 | 지시문을 고치고 오류 원인을 찾는 데 사용 |
| 평가용 | 64 | 33 | 654 | 지시문을 확정한 뒤 처음 열어 성능 계산 |
| 개발 환자의 다른 시험 | 20 | 20 | 146 | 같은 환자가 겹쳐 보조 확인에만 사용 |

개발 환자와 평가 환자는 겹치지 않는다. 같은 환자의 다른 시험은 독립 평가처럼
합치지 않았다.

### 원본 파일의 `training` 표시를 사용하지 않은 이유

이 열은 학습·평가 분할이 아니다. 공개 데이터 카드에는 뜻이 설명돼 있지 않다.
원본을 직접 대조하면 `true` 881행은 공개 GPT 답과 전문가 답이 모두 같고,
`false` 134행은 5행만 같다. 따라서 이 열을 개발용·평가용 자료를 나누는 표시나
성능 비교 기준으로 사용하지 않는다.

공개 TrialGPT 라벨은 논문에 실린 고정 출력이다. 같은 조건에서 다시 실행한 독립
비교모델 결과로 설명하지 않는다.

## 3. 개발 자료 실험

모든 방식에 Claude Sonnet 5 `medium`, 같은 환자 기록, 같은 시험 정보와 같은
구조화 출력을 사용했다. 전문가 라벨과 공개 GPT 결과는 호출이 끝난 뒤에만 열었다.

`not excluded`는 “이 제외 조건 때문에 탈락한다고 볼 근거가 없다”는 TrialGPT의 답이다.
아래의 `찾은 비율`은 전문가가 이 답을 붙인 조건 가운데 모델도 같은 답을 낸 비율이다.

| 방식 | 전체 정답률 | 전문가의 `not excluded`를 찾은 비율 | 전문가가 정보 부족으로 둔 답을 지킨 비율 | TrialGPT만 판단을 미룬 11건 중 맞힌 수 | 비용 |
|---|---:|---:|---:|---:|---:|
| 기존 지시문 | 65.9% | 28.0% | 96.6% | 1/11 | $0.309 |
| 공개 원문에 가까운 지시문 | 72.0% | 46.3% | 93.1% | 2/11 | $0.338 |
| 부재 추론을 엄격히 제한 | 64.0% | 24.4% | 95.4% | 2/11 | $0.355 |
| 기존 지시문 뒤 선택 재검토 | 66.8% | 31.7% | 96.6% | 2/11 | $0.620 |
| 선정·제외 비대칭 규칙 1회차 | 82.5% | 89.0% | 79.3% | 6/11 | $0.388 |
| 선정·제외 비대칭 규칙 2회차 | 80.6% | 86.6% | 77.0% | 7/11 | $0.382 |

비대칭 규칙 두 실행의 라벨 일치율은 88.6%였다. 정확도 방향은 반복됐지만 개별
조건은 흔들렸다.

### 선택 재검토를 기각한 이유

정보 부족이 나온 묶음에 35회 추가 호출했지만 정답은 3건 순증했다. 총비용은
0.620달러였고 한 번 호출 방식보다 느리고 비쌌다. 현재 형태의 선택 재검토는
성능 대비 비용이 낮아 사용하지 않는다.

## 4. 개발에 쓰지 않은 환자 평가

개발 결과를 본 뒤 지시문을 고정했다. 평가 결과에 맞춰 다시 수정하지 않았다.

| 항목 | 기존 지시문 | 선정·제외 비대칭 규칙 |
|---|---:|---:|
| 전체 조건 라벨 일치 | 340/654, 52.0% | 517/654, 79.1% |
| 선정 조건 | 80.6% | 80.6% |
| 제외 조건 | 36.3% | 78.2% |
| 모델이 `not excluded`라고 했을 때 전문가와 같은 비율 | 89.9% | 90.3% |
| 전문가의 `not excluded`를 찾아낸 비율 | 26.3% | 82.8% |
| 전문가 정보 부족 유지 | 83.2% | 74.8% |
| 공개 GPT만 정보 부족, 전문가는 판단 | 6/19 | 10/19 |
| 공개 GPT는 판단, 전문가는 정보 부족 | 16/22 | 13/22 |
| 조건 근거가 있는 행의 근거 완전 일치 | 65.4% | 64.2% |
| 비용 | $1.018 | $1.238 |

균형 규칙은 기존 방식이 틀린 조건 207개를 맞혔고, 기존 방식이 맞힌 조건 30개를
새로 틀렸다. 64개 환자-시험 조합 중 43개에서 더 높았고 5개에서 더 낮았으며,
16개는 같았다. 환자별로는 33명 중 27명에서 더 높고 2명에서 더 낮았다.

성능 상승은 근거 검색이 아니라 최종 라벨 정책에서 주로 나왔다. 선정 조건 성능은
같았고, 기존 방식이 기록에 없는 제외 사유를 지나치게 정보 부족으로 남긴 문제가
줄었다.

### 남은 손실

균형 규칙은 전문가가 정보 부족으로 둔 답을 그대로 지킨 비율을 83.2%에서 74.8%로 낮췄다.
따라서 이 지시문을 현재 자료만으로 참가조건을 확정하는 v5 판정기에 그대로 쓰면
안 된다. TrialGPT 조건 라벨 비교와 넓은 후보 검토에만 사용한다.

## 5. GPT-5.6 Sol 구조 비교

같은 개발 20조합·211조건, 같은 원문과 BM25 결과, GPT-5.6 Sol `medium`으로
비교했다. 첫 실행에서 발견한 구조 문제만 고쳐 두 번째 실행을 진행했다. 두 실행은
모델 출력이 흔들릴 수 있으므로 서로 평균내지 않고, 같은 실행 안의 세 구조를
비교한다.

| 실행 | 구조 | 조건 정확도 | 시험 상태 정확도 | 기록된 토큰 |
|---|---|---:|---:|---:|
| v1 | `S1` 강한 단일 판단 | 72.0% | 85.0% | 368,862 |
| v1 | `M1` 모델 조정 + 판정 | 63.5% | 80.0% | 606,835 |
| v1 | `M2` 모델 조정 + 판정 + 선택 검토 | 64.0% | 85.0% | 797,377 |
| v2 | `S1` 강한 단일 판단 | 68.7% | 80.0% | 367,353 |
| v2 | `M1` 코드 전달 + 판정 | 65.9% | 80.0% | 366,955 |
| v2 | `M2` 코드 전달 + 판정 + 정보 부족 검토 | 65.4% | 80.0% | 678,196 |

v1의 조정 역할은 정해진 전달 답만 만들었다. `M1`과 `M2`를 합쳐 40회 호출과
487,109토큰을 사용했지만 조건 판단에는 관여하지 않았다. 선택 검토는 21개 조건을
골라 2개를 바꿨고, 두 변경 모두 정답을 오답으로 바꿨다.

v2에서는 정해진 전달을 코드로 바꾸고 판단 지침을 `S1`과 맞췄다. 검토 역할은
최초 답이 정보 부족인 131개 조건을 모두 다시 봤다. 라벨 변경은 0개였고 검토 전후
정확도도 같았다. `M2`는 `S1`보다 3.3퍼센트포인트 낮고 토큰은 84.6% 많았다. 근거 선택과
정보 부족 유지도 `S1`보다 높지 않았다.

개발 단계에서 정한 중단 기준에 따라, 매번 검토 모델을 부르는 `M2` 구조는 사용하지
않기로 했다. 개발에 쓰지 않은 환자 64조합에서는 세 구조를 다시 비교하지 않았다.
질문, 기록 조회, 공식 확인과 중단 판단이 있는 전체 v5
멀티에이전트 흐름은 숨은 추가 정보와 다음 행동 정답을 가진 합성 자료에서 따로
검증한다.

## 7. 비용과 실행 자료

이번 반복 개선에서 성공한 호출의 합계 비용은 4.358510달러다. 최초 비용 예비실행과
성공한 연결 확인까지 포함해 이 작업에서 확인한 누적 비용은 4.677448달러다. 이는
API 제공자의 2026-08-20 사용량과 저장된 단가로 계산한 값이며 실제 청구서 전체를
대신하지 않는다.

세부 출력은 `runs/trialgpt-*`에 있다. `runs`와 원본 캐시는 Git에서
무시되므로 GitHub 복구 대상이 아니다. 재현에 필요한 지시문, 자료 분리 코드,
채점 코드와 이 요약 문서는 저장소에서 추적한다.

GPT-5.6 Sol 구조 비교는 ChatGPT 구독 연결을 사용했다. v1은 1,773,074토큰,
v2는 실패 후 재개 기록을 포함해 1,412,504토큰을 기록했다. 개발 실행 뒤 주간
구독 사용률은 15%였다. 이 토큰은 API 청구액으로 환산하지 않는다.

## 8. 한계와 다음 판단

- 개발에 쓰지 않은 환자 평가는 한 번만 실행했다. 최종 모델 비교 수치로 사용하려면 반복이 필요하다.
- 654개 조건은 33명의 환자와 64개 시험 조합 안에 묶여 있어 독립 표본 654개가 아니다.
- 전문가 합의는 TrialGPT 출력을 함께 본 뒤 작성됐으며 완전한 눈가림 정답이 아니다.
- 일부 라벨은 기록 부재를 `not excluded`로 볼지 정보 부족으로 둘지 애매하다.
- 이번 실험은 RAG, 후보 검색, 다음 질문, 후보 유지와 현재 확정 분리를 평가하지 않았다.

기각한 `M2`를 그대로 더 조정하지 않는다. 먼저 선정·제외 비대칭 규칙을 Sol에
정확히 옮기고 두 조건 종류를 나누어 호출해 강한 단일 판단을 다시 만든다. 그 실제
출력 가운데 정보 부족으로 남은 조건만 같은 입력으로 다시 생각하는 검토자를 붙인다.

검토 효과는 세 방식으로 나누어 본다.

1. 규칙을 고친 단일 판단
2. 같은 단일 판단 뒤에 자료 검색 없이 검토
3. 같은 단일 판단 뒤에 제한된 의학 자료 검색을 허용한 검토

검색은 의학 용어의 동의 관계, 질환과 치료의 관계, 중요한 처치가 통상 기록되는지
확인하는 데만 쓴다. 환자에게 없는 사실을 보충할 수 없고, 환자 원문·사례 번호·
TrialGPT 정답을 검색할 수 없다. 검색어, 출처와 확인 날짜를 남기고 같은 결과를
다시 쓸 수 있게 저장한다. 이 비교 뒤에는 v5 합성 사례를 늘려 숨은 추가 사실을
질문·조회·공식 확인으로 얻었을 때 후보 유지와 현재 확정이 알맞게 바뀌는지
측정한다.

후보 시험 검색은 이 조건 판단 비교와 별도로 먼저 검증한다. TrialGPT 공개 코드의
검색어 생성, BM25, MedCPT와 순위 결합을 최소 기준으로 재현하고 TREC 2021에서
개발한 설정을 TREC 2022에서 바꾸지 않는다. 현재 조건별 BM25 결과는 환자 기록을
읽기 위한 문장 안내일 뿐 수만 건에서 관련 시험을 찾은 결과가 아니다. 전체 추천 비교에는 이
최소 기준 이상으로 확인된 같은 후보 검색 결과를 모든 구조에 제공한다.

## 9. TrialGPT의 관련 시험 검색을 우리 환경에서 다시 실행

이 실험은 수만 건의 임상시험 가운데 전문가가 환자와 관련 있다고 표시한 시험을 얼마나
잘 찾아오는지만 검사했다.
참가 조건 판정과 최종 추천은 포함하지 않는다. TrialGPT가 공개한 검색어와 다음 두
검색 방법을 사용했다.

- `BM25`: 환자 설명과 시험 문서에 같은 단어가 잘 겹치는지 본다.
- `MedCPT`: 표현이 달라도 의학적인 뜻이 가까운지 본다.

두 검색 결과를 TrialGPT가 공개한 방법으로 합쳤다. TREC 2021과 2022는 환자 설명과
관련 시험의 정답이 붙은 공개 평가자료이며, 서로 다른 시험 모음을 사용한다.

| 공개 평가자료 | 검색 방식 | 전문가가 관련 있다고 표시한 시험을 검색 결과 상위 500개 안에 남긴 비율 | 관련 시험이 검색 결과 앞쪽에 놓일수록 높아지는 순위 점수 |
|---|---|---:|---:|
| TREC 2021 | BM25 | 79.07% | 66.22% |
| TREC 2021 | MedCPT | 80.44% | 66.25% |
| TREC 2021 | 두 검색을 합침 | **83.59%** | **69.97%** |
| TREC 2022 | BM25 | 78.75% | 66.98% |
| TREC 2022 | MedCPT | 78.95% | 66.83% |
| TREC 2022 | 두 검색을 합침 | **81.55%** | **70.11%** |

두 검색을 합치면 같은 단어만 찾는 BM25보다 전문가가 관련 있다고 표시한 시험을 검색
결과 상위 500개 안에 남긴 비율이
2021년 자료에서 4.52퍼센트포인트, 2022년 자료에서 2.79퍼센트포인트 높았다. TrialGPT
논문의 결과표와 우리가 다시 실행한 값은 가장 크게 다른 항목도 0.0932퍼센트포인트
차이였다. 소수점 첫째 자리로 반올림하면 모두 같은 결과다.
여러 문서를 한꺼번에 처리해도 한 문서씩 처리했을 때와 검색 순위가 달라진 증거는
없었다.

앞으로 관련 시험 검색이 필요한 모든 비교에는 이 결합 검색 결과를 똑같이 제공한다.
이전에 BM25만 사용한 조건 판단 실험은 환자 기록 안에서 읽을 문장을 표시한 것이지,
수만 건에서 시험을 찾은 실험이 아니다. 검색 결과의 순서를 더 손보는 기능은 정답
시험을 놓치는 비율이 늘지 않을 때만 사용한다.

이번 검색에는 외부 모델 사용료가 들지 않았다. TrialGPT가 공개한 검색어를 그대로
사용했으므로 검색어를 만드는 모델의 성능은 다시 검사하지 않았다. 실행 환경은 RTX
5060과 CUDA 13.0 대응 PyTorch를 사용했다. 프로그램 버전 차이로 같은 점수를 받은
시험의 순서가 조금 달라진 경우도 위 차이에 포함했다. 원본 시험 모음, 검색 계산값과 실행 결과는
`runs/trialgpt-retrieval` 및 `.research-cache`에 있으며 Git에는 넣지 않는다.

## 10. 강한 단일 판단과 두 검토 방식

기존 Sol 단일 판단에 빠졌던 선정·제외 비대칭 규칙을 옮기고, 선정 조건과 제외
조건을 서로 다른 호출로 나눴다. 그 한 번의 실제 출력을 복사해 두 검토 방식에
똑같이 제공했다. 검토자가 별도 판정기를 다시 실행하던 이전 `M2`와 다르다.

첫 실행에서는 정보 부족 93개를 모두 검토했다. 단일 판단은 75.4%였고 두 검토는
각각 정답 1개를 추가해 75.8%였다. 인터넷 검토자는 검색을 사용하지 않아 검색 없는
검토와 결과가 같았다.

두 번째 실행에서는 최초 판단이 강한 추론·기록 부재·근거 충돌의 경계라고 표시한
21개만 검토했다. 인터넷 검토에는 호출당 일반 의학 검색 1~3회를 요구했다. 환자
문장, 환자·시험 식별자, 조건 원문, TrialGPT와 정답 라벨 검색은 코드로 거부했다.

| 방식 | 조건 정확도 | 시험 상태 정확도 | 정보 부족 유지 | 검토 변화 | 구조 전체 토큰 |
|---|---:|---:|---:|---:|---:|
| `S1-R` 강한 단일 판단 | 160/211, 75.8% | 16/20, 80.0% | 75.9% | — | 628,625 |
| `S1-RV` 검색 없는 집중 검토 | 160/211, 75.8% | 16/20, 80.0% | 74.7% | 정답 추가 1, 정답 훼손 1 | 793,592 |
| `S1-RW` 인터넷 집중 검토 | 158/211, 74.9% | 15/20, 75.0% | 73.6% | 정답 추가 0, 정답 훼손 2 | 875,339 |

두 번째 실행에서 실제 사용한 토큰은 1,040,306개다. 세 구조의 토큰은 각 구조를
독립적으로 사용할 때 단일 판단 비용을 포함한 값이므로 서로 더하지 않는다. 인터넷
검토는 12회 검색했고, 검색어와 결과 URL은 호출 기록에 남겼다. 구독 사용률은 실행
전후 모두 17%로 표시됐다.

강한 단일 판단의 오답 51개 중 47개는 판단 가능과 정보 부족 사이의 경계였다.
검색 없는 검토는 `경구약을 복용하고 유지할 능력`을 올바르게 확정했지만, 영상으로
확인되지 않은 만성 경막하혈종을 증상만으로 확정해 같은 수의 정답을 잃었다. 인터넷
검토는 일반 의학 관계를 확인했지만 환자에게 없던 사실을 보충할 수 없었고, 임신 중
철분 복용 시점과 시술 중 의사소통 능력을 과도하게 추론해 두 정답을 잃었다.

따라서 질문 없이 한 번 판단하는 TrialGPT 조건 실험에서는 두 검토 방식을 사용하지 않는다. 인터넷을 열면 지식은
늘지만 환자별 증거는 늘지 않으며, 이번 자료에서는 오히려 과확정이 증가했다. 개발
20조합을 보며 검토 규칙을 더 조정하지 않는다. 답 이름을 그대로 채점한 점수는 공개
TrialGPT보다 낮지만, 오답 51개 중 47개가 `판단 가능`과 `정보 부족`의 경계였다.
이 프로젝트에서는 두 답이 모두 후보 유지로 이어지며, 다음 절의 실제 후보 유지·제외
결과는 98.1%가 전문가와 같았다. 이 범위에서는 거의 모두 맞춘 셈이다. 따라서 답
이름을 맞추기 위해 더 조정하지 않았다. 답을 그대로 세는지 실제 결과로 묶는지에 따라
통계가 달라지며, 어느 쪽도 v5 전체 성능은 아니다.

## 11. 한 번 판단한 결과를 후보 유지·제외 행동으로 다시 계산

조건 라벨이 아니라 실제 후보 유지·제외 행동으로 `S1-R` 개발 20조합을 다시
집계했다. `included`, `not excluded`, `정보 부족`과 `적용 대상 아님`은 후보 유지,
`not included`와 `excluded`는 후보 제거로 옮겼다.

| 단위 | 행동 일치 |
|---|---:|
| 조건 211개 | 207/211, 98.1% |
| 환자-시험 20조합 | 17/20, 85.0% |

시험 세 개만 후보 행동이 달랐다. 두 시험은 모델이 제외했지만 전문가 정답은
유지였고, 한 시험은 전문가 정답이 제외였지만 모델이 추가 확인 후보로 남겼다.
세 사례에는 광범위한 `의학적 질환`, 활동성 신장 루푸스의 간접 근거, 시행하지 않은
CT와 인공호흡 기록 부재처럼 정답 정책에 따라 달라질 수 있는 조건이 포함됐다.

이 계산은 한 번 판단하는 모델이 다음 질문 실험으로 넘어갈 만큼 작동함을 보여주지만,
개발 20조합의 사후 분석이므로 최종 성능으로 사용하지 않는다. TrialGPT 라벨
정확도는 비교용 보조지표로 유지하고, v5 주 실험은 후보 유지·제외 판단이 모든 정보를
알 때의 판단과 같아진 비율, 잘못된 후보
제거, 너무 이른 확정과 질문 수를 평가한다.

작동 확인 결과로만 보고한다.

## 13. 전수 질문 결정 트리 진단

평가 환자의 실제 숨은 답을 정책에 주지 않고, 사실별 통과·위반 값, 식별자와 출처 위치를
별도의 계획 자료로 만들었다. 실제 숨은 답은 행동을 실행한 뒤에만 환자 상태에서 읽는다.
5개 사실의 32개 가능한 전체 환자 상태와 남은 행동 3회의 질문·답변 가지를 모두
계산했다. 답의 분포를 믿을 수 있을 때 쓰는 평균 우선 방식과, 분포를 믿기 어려울 때 쓰는
최악 우선 방식을 분리했다. 최악 우선 방식은 가장 불리한 답에서도 모든 정보를 알 때와
같은 판단에 도달한 시험 비율이 같은 질문 사이에서 평균 결과로
순서를 정한다.

- 12명 반복 작동 확인: 평균 우선·최악 우선 전수 계산, 영향 규칙과 비용 규칙은 모두 모든 환자 정보를 알 때와 같은 시험 판단에 100% 도달
- 불균형 답 진단: 연결 수만 보는 규칙은 현재 결정에 거의 도움이 없는 BMI를 골랐고, 평균 우선 전수 정책은 주사 치료 의사를 골랐다.
- 분포 불확실성 진단: 한 검사가 99% 확률로 두 시험을 끝낸다고 가정하면 평균 우선 방식은 그 검사를 고른다. 최악 우선 방식은 답과 관계없이 시험 하나를 끝내는 환자 질문을 골라, 모든 정보를 알 때와 같은 판단에 도달하는 시험 비율을 최소 33.3%로 유지했다.
- 5개 정보: 분기 상태 131개, 12명 실행은 명령 전체 1.7초
- 10개 정보: 가능한 환자 상태 1,024개, 분기 상태 1,161개, 계획 준비 0.68초·첫 선택 0.36초
- 15개 정보: 가능한 환자 상태 32,768개, 분기 상태 4,091개, 계획 준비 27.83초·첫 선택 0.98초

첫 구현은 15개 실행에서 4분 내 완료하지 못했다. 가능한 환자 집합을 비트로 표현하고 동일 관측 상태를
재사용하도록 바꾼 뒤 전체 준비와 선택이 약 31초에 끝났다. 현재 범위에서는 근사 정책으로 바꿀
실용적 필요가 없다. 후보 시험 묶음이 바뀐 때 약 28초의 준비 계산을 한 번 수행하고, 환자 답변 뒤 다음 질문은
1초 안에 다시 선택할 수 있다.

최악의 결과만 비교하고 바로 행동 수로 동률을 깬 첫 방식은 12명 실제 가지에서 60%의
시험만 모든 정보를 알 때의 판단과 같아졌다. 가장 불리한 답의 결과가 같을 때 평균 결과를
두 번째 기준으로 추가하자 100%가 같아졌다. 이는 최악 우선
계산도 평균 결과를 완전히 무시하면 불필요하게 방어적으로 변한다는 진단 결과다.

현재 12명은 구조가 반복되고 모든 판정기가 자료 부족 상태에서 후보 제거와 적합 확정을 하지 않도록
작성되어 있다. 따라서 잘못된 제거와 너무 이른 확정이 0인 것은 질문 정책의 안전성을 입증하지 않는다.
주 실험에는 오래된 자료, 허용되지 않은 출처, 서로 충돌하는 자료와 아직 끝나지 않은 확인 절차를
넣어 이 두 오류가 실제로 발생할 기회를 만들어야 한다. 또한 사실별 독립 이진 분포는 코드 진단용이며,
주 실험은 함께 나타날 수 있는 환자 전체 상태를 묶어 사용해야 한다.

## 14. 질문 연결 구조 700개 검사

공통 사실 하나가 여러 시험에 연결된 구조, 사슬형 구조, 서로 겹치는 구조, 확인
비용이 충돌하는 구조 등 일곱 종류를 각각 100개씩 만들었다. 구조마다 숨은 사실
5개, 후보 시험 5개, 행동 한도 3회를 사용했다. 실제 숨은 답과 개발용 답 분포는
식별자와 자료 위치까지 분리했다.

| 비교 | 개발과 비슷한 분포 | 개발과 다른 분포 |
|---|---:|---:|
| 한 단계 평균 우선 - 단순 동적 규칙 | +3.81퍼센트포인트 | +1.40퍼센트포인트 |
| 전체 평균 질문 나무 - 한 단계 평균 우선 | +0.25퍼센트포인트 | +0.20퍼센트포인트 |
| 한 단계 최악 우선 - 단순 동적 규칙 | +2.21퍼센트포인트 | +2.41퍼센트포인트 |

여러 질문을 미리 끝까지 계산한 추가 이득은 0.25퍼센트포인트 이하였다. 따라서 전체 질문
나무는 기본 구조 후보에서 제외했다. 한 단계 계산은 실제 공개 조건에서 다시
검사하기 위한 비교군으로만 남겼다. 이 결과는 임상 조건이 아닌 연결 구조 검사다.

## 15. 공개 조건 기반 합성 환자 30명

ClinicalTrials.gov에서 2형 당뇨병, 유방암, 주요우울장애 시험을 각각 5건씩 받았다.
공개 원문에서 객관적으로 계산 가능한 조건 80개를 구조화하고, 가상 환자 30명을
개발 10명과 평가 20명으로 나눴다. 환자마다 서로 다른 정보 조합을 가린 버전
두 개를 적용해 총 60회를 실행했다. 각 버전에는 처음 보이는 정보 2개와 숨긴 정보
5개가 있으며, 질문 계획은 실제 숨은 답을 읽지 않는다.

개발 자료에서 가장 강한 단순 방식을 먼저 고정한 뒤 20명에게 적용했다.

| 환자 한 명당 추가 확인 한도 | 개발 환자에서 고른 간단한 정보 선택 기준 | 선택한 기준의 결과 | 가능한 답들의 평균에서 가장 많은 시험 판단을 끝내는 정보를 계산 | 가장 불리한 답에서도 가장 많은 시험 판단을 끝내는 정보를 계산 |
|---:|---|---:|---:|---:|
| 1회 | 통과·위반 가능성이 비슷한 정보부터 확인 | 54.5% | 59.0% | 57.0% |
| 2회 | 영향받는 시험 수를 확인 비용으로 나눈 값이 큰 정보부터 확인 | 71.0% | 75.0% | 69.0% |

평균 우선 계산의 이득은 각각 4.5퍼센트포인트, 4.0퍼센트포인트, 2.0퍼센트포인트였고 매번 확인 비용이 더
들었다. 미리 정한 채택 기준인 “모든 환자 정보를 알 때와 같은 판단에 도달한 시험
비율 5퍼센트포인트 향상” 또는 “그 비율이 같을 때 부담 20%
감소를 어느 설정에서도 통과하지 못했다. 최악 우선 계산도 통과하지 못했다.

여기서 확인 비용은 `환자 질문=1`, `기록 조회=2`, `공식 확인=3`으로 둔 간이
실험값이다. 기존 공식 결과 확인과 새 검사를 구분하지 않았으므로 실제 환자 부담이나
의료비로 해석하지 않는다. 이 한계를 나눈 환자의 이동·비용·시간 제한을 반영한 확인 방법 선택 구조 실험은 17절에
별도로 기록한다.

## 16. 공개 조건 값 77,792조합 전수 검사

30명에게 우연히 맞은 결과인지 확인하기 위해 공개 조건표에 선언한 가능한 환자 값
77,792조합을 모두 계산했다. 처음 보이는 정보의 조합은 92개였고, 일곱 정책을 합쳐
544,544개의 정책·환자 상태를 비교했다. 외부 모델 호출은 없었다.

평균 우선 계산은 개발 자료에서 단순 규칙보다 0.4퍼센트포인트 높았지만, 개발에
사용하지 않은 평가 자료에서는

질환과 정보를 가린 버전별 결과도 모두 단순 규칙보다 낮았다. 가장 불리한 답을 우선한 계산도 평가 자료에서 0.9퍼센트포인트
낮았다.

당시 결론은 다음과 같았다. 답의 확률까지 가정한 복잡한 계산은 작은 구조 실험에서는 약간의 가능성을 보였지만 실제
공개 조건 연결에서는 이득이 유지되지 않았다. 전수 계산과 최악 우선 계산을 최종
구조에 넣지 않는다. 더 많은 미해결 후보와 조건에 연결된 사실을 먼저 확인하고,
동률이면 부담이 낮은 경로를 고르는 단순 동적 규칙을 현행 질문 선택 방식으로 남긴다.
25절에서 채택한 방법은 답의 확률이나 가능한 답의 가지를 계산하지 않는다. 남은 확인
횟수 안에서 고를 수 있는 부족 정보 조합을 모두 비교해, 가장 많은 시험 판단을 끝내는
조합을 고르므로 이 절에서 기각한 방법과 다르다.

이번 평가는 연구자가 구조화한 공개 조건과 합성 환자를 코드로 계산했다. 자연어
조건 추출, 자연어 환자 기록 해석, 의료진 정답과 실제 임상 성능은 평가하지 않았다.
잘못된 후보 제거와 너무 이른 확정이 0인 것도 결정 규칙이 보수적으로 작성된 결과이므로
임상 안전성 증거로 사용하지 않는다.

## 17. 환자의 이동·비용·시간 제한을 반영한 확인 방법 선택 구조 실험

이 절은 남은 확인 횟수까지 고려하는 정보 선택 방법을 연결하기 전의 첫 부담 모듈
결과다. 그 정보 선택 방법을 연결해 다시 실행한
현재 보고값은 25.5절과 [보고서·발표 정리본](CLARIFYTRIAL_REPORT_PRESENTATION_PACKET.md)을
사용한다.

### 17.1 실행 조건

- 공개 시험 15건, 구조화 조건 80개, 합성 환자 30명
- 환자마다 정보를 가린 버전 2개, 환자 부담 상황 3개, 자료 가용성 2개
- 총 360개 환자·자료 상황, 다섯 방식, 1,800개 정책 실행
- 개발 환자 10명 120개 상황, 정보 선택 방법을 만드는 데 사용하지 않은 환자 20명 240개 상황
- 확인 한도 3회
- 외부 모델 호출 0회, 입력·출력·추론 토큰 0개
- ClinicalTrials.gov 원문 대조 조건 80개 모두 통과

비교 방법은 가장 많은 시험에 연결된 정보 우선, 모든 환자에게 같은 비용표 적용,
추가 부담이 가장 작은 방법 우선, 환자의 이동·비용·시간 제한 반영이다. 모든 정보를
확인하는 내부 진단 실행도 만들었지만 환자 부담 결과에는 보고하지 않는다.
자료 가용성은 기존 자료 중심과 새 확인 필요로 나눴다. 환자 상황은 추가 부담이 낮은
경우, 이동·비용 제약, 시간 긴급으로 나눴다.

### 17.2 구현 중 수정한 오류

첫 실행에서는 이동·비용 부담이 큰 환자가 이용할 수 없는 새 검사까지 시행한 결과를
채점 기준으로 삼아, 환자 한도를 지킨 방식이 자동으로 낮은 점수를 받았다. 주 지표를
“실제로 이용할 수 있는 방법만 써서 최종 판단까지 맞게 끝낸 시험”으로 바꿨다.

시간이 급한 환자에서 대기 시간만 먼저 보자 영향이 작은 빠른 정보를 골라, 모든 환자
정보를 알 때와 같은 판단에 도달한 시험 비율이 낮아졌다.
후보·조건 영향을 먼저 지키고 영향이 같을 때 대기 시간을 줄이도록 수정했다. 또한
기존 공식 결과가 있는데 별도 의료진 평가를 선택할 수 있던 경로를 막았다. 이 수정은
개발 자료에서 했고, 정보 선택 방법을 만드는 데 사용하지 않은 환자 20명의 결과에 맞춰
다시 바꾸지 않았다.

| 환자가 명시한 한도 위반 | 0건 | — | 채택 기준 충족 |

환자의 이동·비용·시간 제한을 반영해 확인 방법을 고르는 방식은 이동이나 비용 때문에 새 검사·추가 방문이 어렵다고 입력된 환자에게
기존 기록, 이미 받은 결과와 환자 답변처럼 실제로 이용할 수 있는 방법을 먼저 사용했다.

개발 환자와 개발에 사용하지 않은 환자에서 변화 방향이 같았고, 미리 정한 채택 기준을
모두 통과했다.
구조화 공개 조건 실행기에서는 환자의 이동·비용·시간 제한을 반영하는 규칙을 후속 기본 비교 방식으로 유지한다.

### 17.4 한계

부담 단계, 대기 시간과 자료 가용성은 연구진이 만든 합성값이다. 100% 새 검사·방문
감소는 새 검사를 거부한 합성 상황을 넣은 결과이므로 실제 환자 편익으로 해석하지
않는다. 실제 비용, 예약 가능성, 의료적 필요성과 환자 선호 정답은 없다. 사람 승인
경계와 부담 단계는 의료 전문가 검토가 필요하다. 자연어 시험 원문과 환자 기록을
읽는 전체 에이전트 흐름에서도 같은 결과가 나오는지는 아직 측정하지 않았다.

재현 명령은 다음과 같다.

```powershell
.\.venv\Scripts\clarifytrial.exe run-public-burden-benchmark `
  --source-cache .research-cache\clinicaltrials-v5 `
  --output runs\patient-burden-v1 `
  --action-budget 3
```

## 20. 원문 서식 허용과 핵심값 보호 검사

### 20.1 바꾼 이유

첫 연결은 모델이 적은 인용문의 띄어쓰기와 글자 위치가 원문과 정확히 같아야 통과했다.
이 방식은 근거 위치를 남기는 데는 도움이 되지만, 줄바꿈 하나 때문에 올바른 수치까지
버릴 수 있어 의료 판단의 정확성과 직접 관계가 약했다. 위치는 코드가 다시 찾고,
판정을 바꾸는 내용만 엄격하게 확인하도록 바꿨다.
환자 상태표와 시험 조건표에는 모델이 다시 쓴 설명 대신 코드가 찾은 실제 원문을
저장한다.

### 20.2 변형 검사

| 변형 | 결과 |
|---|---:|
| 공백 제거, 줄바꿈·탭, 대소문자, 전각 문자, 보이지 않는 공백 5개 | 5/5 허용 |
| 틀린 위치 힌트지만 근거 문구가 한 곳에 존재 | 허용하고 코드가 위치 재계산 |
| 원문에 없는 환자 수치·날짜, 시험 역치·비교 방향·기간·공식 출처 7개 | 7/7 거부 |
| `%`·`percent`, 유니코드 지수 등 같은 단위 표기 3개 | 3/3 동일 단위 처리 |
| `mg/dL`·`mmol/L`처럼 환산이 필요한 단위 | 동일 단위로 처리하지 않음 |

### 20.3 전체 구조 검토에서 수정한 문제

숫자 조건은 코드가 수치·날짜·출처를 계산한 뒤에도 모델이 다른 판단을 반환하면
모델 답을 유지하고 선택 검토로 보내고 있었다. 검토자가 이를 승인하면 코드 계산이
무시될 수 있었다. 이제 계산 가능한 숫자 조건은 코드 결과가 최종값이다. 모델의 다른
답은 코드값으로 교정하고 교정 전후를 실행 기록에 남긴다. 숫자가 없는 복합 조건과
부정·예외 해석은 여전히 모델 판단과 선택 검토 대상이다.

의도적으로 모델이 오래된 혈소판 결과를 `위반·근거 충분`이라고 답한 검사에서 코드는
이를 `기준 지지·근거 불충분`으로 교정했고 후보를 유지했다. 선택 검토 호출은 발생하지
않았다. 이후 검사명 표기와 후보 검색어 경계를 보강한 상태에서 전체 자동 검사 195개가
통과했다.

이 결과도 구조 검사다. 제한된 영어·한국어 표현에서 핵심값 보호가 작동했다는 뜻이며,
다양한 실제 프로토콜 문장을 모두 해석하거나 단위 환산을 정확히 수행한다는 뜻은 아니다.

두 검토자가 조건 포함 여부와 수치·비교 방향·기간·자료 출처를 각각 작성한 뒤,
불일치만 원문을 다시 보고 합의한다.

### 22.3 자체 검토에서 고친 문제

- `Without Type 2 Diabetes`처럼 질환이 없다는 시험이 당뇨병 후보에 들어가던 문제를
  막았다.
- `3.1 Inclusion Criteria` 같은 번호가 붙은 제목을 실제 조건으로 세던 문제를 고쳤다.
- 원문 한 줄에 조건이 둘 이상일 때 같은 원문을 여러 조건으로 나눠 기록할 수 있게 했다.
- 저장한 원문을 다시 쓸 때 수집 날짜가 실행 날짜로 바뀌던 문제를 고쳤다.
- 사람이 작성하기 시작한 검토표를 일반 실행이나 원문 갱신이 덮어쓰지 못하게 했다.
- 자동 탐지된 164줄만 검토하면 빠뜨린 조건을 발견할 수 없으므로 조건 원문 272줄을
  모두 검토하도록 바꿨다.
- 숫자가 없는 명시적 상태도 정답 후보로 표시할 수 있게 수치 칸을 선택 항목으로 바꿨다.
- 한 원문을 두 조건으로 나눈 행이 원문 감사에서 오류로 처리되던 문제를 고쳤다.

### 22.4 해석 범위

이 결과는 공개 원문을 고정하고 두 사람 검토를 시작할 준비가 됐다는 뜻이다. 아직 두
사람의 검토와 합의가 없으므로 272줄을 정답 조건이라고 부를 수 없다. 환자 30명과
질문 전후 상태도 아직 만들지 않았고, 에이전트 성능·의사 일치도·TrialGPT 대비 성능은
측정하지 않았다.

## 23. 새 시험 조건의 AI 단독 예비 검토

### 23.1 실행과 수정

272줄 전체를 GPT-5.6 Sol `medium`으로 초안 작성과 독립 재검토 두 번에 걸쳐 읽었다.
이후 애매하거나 중간 확신인 105줄을 `max`로 다시 확인했다. 자체 표본 검사에서
`임신이면 제외`를 `임신하지 않음`으로 뒤집은 사례를 발견해 지시문을 고쳤다. 마지막으로
당시 채택된 128줄을 `max`로 다시 읽어 조건이 참이 되는 환자 상태를 일관되게 맞췄다.
`max`는 [OpenAI의 GPT-5.6 Sol 모델 설명](https://developers.openai.com/api/docs/models/gpt-5.6-sol)에
기재된 가장 높은 API 추론 수준이다.

| 항목 | 결과 |
|---|---:|
| 검토한 원문 | 272줄 |

`runs`에만 보존했다.

### 23.2 코드 검사

- 검토 결과가 고정 원문 272줄을 빠짐없이 한 번씩 다루는지 확인했다.
- 원문 문구, 줄 번호와 글자 위치가 바뀌면 예비 정답 생성을 중단한다.

교체와 새 합성 환자 제작 결과는 24절에 기록한다. 아직 에이전트 성능은 측정하지 않았다.

복원하고, 시험 번호·원문 해시·줄 위치와 후보 수를 대조했다.
Windows와 Linux에서 같은 파일의 줄바꿈만 달라 해시 검사가 실패하지 않도록 텍스트

### 24.3 환자와 근거 상태 짝

질환별 10명, 총 30명의 구조화된 합성 환자를 만들었다. 개발 자료는 당뇨병 4명,
유방암 3명, 주요우울장애 3명으로 총 10명이고, 나머지 20명은 정보 선택 방법을 만드는

환자마다 다섯 사실의 임상값을 고정하고 자료 상태만 다음처럼 바꿨다.

- 충분한 상태: 환자에게 직접 확인할 사실은 답변 완료, 기록으로 볼 사실은 확인된
  의료기록으로 표시
- 부족한 상태: 같은 값이지만 환자 답변 대기 또는 기록 미확인으로 표시

각 질환의 다섯 사실은 다섯 후보 시험을 모두 덮도록 골랐다. 예를 들어 당뇨병에서는
나이, 체질량지수, 영어 가능 여부, 당화혈색소와 수면장애 진단을 사용한다. 유방암은
나이와 혈구 수치, 과거 치료 수와 칼슘 수치, 우울장애는 나이·체질량지수·불면 점수·
진단과 니코틴 중단 가능 여부를 사용한다.

판단이 나오지 않은 경우는 0건이었다.

ClarifyTrial을 아직 실행하지 않았으므로 어느 구조가 더 정확하다고 말할 수 없다.
92조건은 공개 원문과 미리 정한 규칙으로 만든 연구용 예비자료다. 다음 실행은 개발
환자 10명에서 자연어 구조화 정확도를 확인하고, 그 결과로 지시문을 고친 뒤 고정
평가 20명을 여는 순서다.

## 25. 합성 자연어 기록과 질문 정책 예비평가

### 25.1 무엇을 비교했는가

AI 단독으로 검토한 공개 시험 15건·92조건을 사용했다. 조건은 숫자나 예·아니오로
계산할 수 있으므로 모델에게 같은 조건 판단을 여러 번 반복시키지 않았다. Sol은 합성
환자 기록에서 값·단위·자료 출처·확인 상태를 읽고, 이후 후보 유지·현재 확인·질문
선택과 다시 판단은 같은 코드가 맡았다.

| 방식 | 추가 정보 사용 | 질문 순서 |
|---|---|---|
| 추가 정보를 확인하지 않고 처음 환자 자료만 사용하는 방법 | 없음 | 해당 없음 |
| 처음 빠진 정보 목록에 적힌 순서대로 확인하는 방법 | 최대 5개 | 시험 원문에 먼저 나온 부족 사실부터 |
| 가장 많은 시험에 연결된 정보부터 확인 | 최대 5개 | 현재 영향을 받는 시험 수가 많은 사실부터 |
| 남은 확인 횟수 안에 가장 많은 시험 판단을 끝낼 정보 조합을 계산 | 최대 5개 | 남은 횟수 안에 끝낼 수 있는 시험 수가 가장 많은 사실 묶음 |

모든 방식은 같은 환자 기록 해석 결과, 같은 후보 시험과 같은 숨은 확인 답을 사용했다.
질문 방식만 달랐다. 인터넷 검색은 사용하지 않았다.

### 25.2 자연어 기록 제작과 해석

구조화된 환자 사실을 진료기록형과 문장형으로 반씩 표현했다. 충분한 근거와 부족한
근거의 짝은 임상값과 문장 순서가 같고 자료 출처·확인 상태만 다르다. 생성 뒤에는
모든 값·단위·출처·확인 상태를 원래 상태표와 다시 대조했다.

| 실행 | 기록 | 핵심 항목 정확도 | 없는 항목 생성 | 토큰 |
|---|---:|---:|---:|---:|
| 첫 자료 개발 | 20 | 100% | 0 | 293,607 |
| 첫 자료 평가 | 40 | 100% | 0 | 588,901 |
| 새 환자 평가 | 30 | 100% | 0 | 444,406 |
| 합계 | 90 | 100% | 0 | 1,326,914 |

첫 자료는 연결과 정책 약점을 찾는 개발 자료로 사용했다. 최종 질문 규칙을 정한 뒤
질환별 10명, 총 30명의 새 환자를 평가 자료로 만들었다. 새 자료는 부족한 근거 기록만
Sol `medium`으로 읽혔다. 30회 모두 값·단위·자료 출처·확인 상태를 맞혔고 실패와
재시도는 없었다.

100%는 실제 진료기록 성능이 아니다. 문장은 정해진 생성 틀을 사용하고 확인 상태도
읽을 수 있게 표현했다. 이 결과는 모델 해석 오류 없이 질문 정책을 비교할 수 있다는
연결 검사로 해석한다.

### 25.3 첫 규칙에서 찾은 문제

첫 환자 20명의 평가 부분에서 확인을 세 번 허용하면 가장 많은 시험에 연결된 정보부터
확인한 방법이 입력 목록 순서대로 확인한 방법보다 높았다. 그러나 한 번만 허용하면
각각 50%와 54%였다. 여러 시험에 걸친 정보가
항상 한 시험을 바로 끝내는 정보는 아니기 때문이다.

이 결과 뒤에 첫 30명은 모두 개발 자료로 돌렸다. 남은 확인 횟수 안에 가장 많은 시험
판단을 끝낼 정보 조합을 계산하는 방법은 후보 사실이 5개일 때 가능한
32개 조합을 전부 살펴 다음을 계산한다.

1. 남은 질문 횟수 안에서 판단을 끝낼 수 있는 시험 수
2. 동률일 때 영향을 받는 시험 수
3. 다시 동률일 때 영향을 받는 조건 수

숨은 답이나 답의 확률은 계산에 넣지 않는다. 사실을 고른 뒤 확인 경로는 별도의 환자
부담·자료 가용성·사람 승인 규칙이 정한다.

### 25.4 새 환자 30명의 결과

각 환자는 후보 시험 5개와 부족 사실 5개를 가진다. 질문 횟수 0~5회를 모두 계산했다.

### 25.5 일반 환자 실행에 연결한 결과

남은 확인 횟수 안에 가장 많은 시험 판단을 끝낼 정보를 고르는 방법을 일반 환자 실행에

확인 방법과 환자 한도 위반을 먼저
제외하고, 같은 사실의 경로는 기존 자료를 새 검사보다 우선한다.

각각 80회다. 아래 첫 두 행은 이동·비용 부담 80회, 마지막 행은 시간 긴급 80회의

### 25.6 후보 검색을 붙이지 않은 이유

현재 새 자료는 질환별 시험 5개, 전체 15개뿐이고 입력에도 질환 범위가 주어진다. 이
임상시험 문서 15건에서 후보 검색 점수를 내면 답이 거의 드러나 질문 순서나 실제 검색 능력을

정답이 있는 TREC 2021·2022 재현 결과로 분리해 유지한다.

후보 검색을 포함한 전체 추천 평가는 질환 정답을 직접 주지 않는 환자 질의와 충분한
관련 없는 임상시험 문서를 충분히 포함한 자료를 만들 때 연다.

## 27. 값이 완전히 빠진 입력, 질문 집계와 텍스트 화면

| 4 | 96.7% | 3.47 | 2.73 |
| 5 | 100.0% | 3.63 | 2.90 |

이 결과는 값이 보이지만 출처 확인이 부족했던 25절 결과와 같았다. 현재 자료에서는
두 입력 모두 핵심 조건을 미정으로 남기므로 시험 단위 판정이 같았기 때문이다. 따라서

같은 질문 정책과 다시 판단 절차가 끊기지 않았다는 구조 검사다.

### 27.2 질문이 실제로 필요했는지 계산

실행이 끝난 뒤에만, 같은 질문 한도 안에서 가능한 정보 묶음을 모두 시험했다. 가장
좋은 결과를 내는 가장 작은 정보 묶음이 여러 개면 모두 정답으로 허용했다. 이 정답은
질문을 고르는 코드에는 전달하지 않았다.

추가 확인을 세 번 허용했을 때, 가장 많은 시험 판단을 끝낼 정보를 매번 계산한 방법은
30명 모두 최종 판단에 필요했던 정보를 골랐다. 총 88개 정보를 확인한 뒤 그중 어떤
시험의 판단도 더 바꾸지 못한 정보는 9개, 환자당 평균 0.30개였다. 입력 파일에 적힌
순서대로 확인한 방법은 최종 판단에 필요했던 정보 중 61.1%를 골랐고, 어떤 시험의
판단도 더 바꾸지 못한 정보는 환자당 평균 1.37개였다. 모든 환자 정보를 알 때의
판단과 같아진 시험 비율은 두 방법이 각각 88.7%와 75.3%였다.

이 “필요 여부”는 정해진 합성 답을 본 뒤 계산한 평가값이다. 실제 실행 중에는 답을
미리 알 수 없으므로, 결과를 바꾸지 않은 9번을 모두 사전에 피할 수 있었다고 주장하지
않는다.

### 27.3 참가 조건 불충족 기준과의 차이

객관적인 숫자나 기간 조건이 충분한 근거로 참가 조건 불충족을 만들었을 때 다음 값을
결과에 추가한다.

- 현재 값과 단위
- 기준값과 비교 방향
- 현재 값이 기준보다 얼마나 높거나 낮은지
- 사용한 환자 근거와 임상시험 조건 원문 위치

예를 들어 `100일 이상`이 필요한데 현재 값이 `92일`이면 `기준보다 8일 낮음`으로
표시한다. 예·아니오 조건과 근거가 부족한 조건에는 계산하지 않는다. 서로 다른 검사,
점수와 기간의 차이를 한 순위로 합치지 않는다. 이는 치료나 새 검사를 권하는 기능도
아니다.

### 27.4 과정이 보이는 텍스트 화면

`run-text-demo` 명령을 추가했다. 처음 판정, 다음에 확인할 정보와 선택 이유, 확인 방법,
검증용 합성 답변, 답변 뒤 바뀐 시험과 최종 판정을 순서대로 보여 준다. 기본 실행은
각 답변 전에 Enter를 기다리고, `--auto`를 붙이면 멈추지 않고 끝까지 출력한다.

```powershell
.\.venv\Scripts\clarifytrial.exe run-text-demo `
  --patient-id natural-breast_cancer-11 `
  --input-state fully-missing `
  --action-budget 3 `
  --auto `
  --output runs\text-ui-demo.json
```

외부 모델과 인터넷 검색은 사용하지 않는다. 화면에 나오는 환자와 답변은 모두 합성
자료이며 마지막에는 학생 과제용 결과라고만 표시한다.

- 모델: GPT-5.6 Sol `medium`

시스템은 나이, 영어 의사소통 가능 여부, 수면장애 진단 여부를 차례로 확인하고 관련
조건만 다시 판단했다. 실제 호출은 진행 관리 9회, 검색·판단 9회, 다음 확인 문장 작성
3회, 선택 검토 1회로 총 22회였다. 제공자 보고 사용량은 321,910토큰이다.

실행은 오류 없이 결과와 단계별 기록을 저장했다. 선택 검토 한 번을 사용한 뒤에도
사람이 다시 볼 결론이 남아 `human_review` 상태로 끝났다. 확인한 세 사실을 모델이
끝내 충분한 근거로 처리하지 않은 조건도 있었다. 화면에서는 이를 아직 묻지 않은
정보와 구분해 `확인했지만 판단이 끝나지 않은 정보`로 표시한다. 이 실행은 통합 화면이
전체 경로를 연결했다는 검사이며 조건 판단 성능이나 최종 추천 성능 결과가 아니다.
15개 시험 안에서 질환을 먼저 맞춘 뒤 문구 순서를 정한 검색이므로, 수만 건을 사용한
TrialGPT식 검색 재현 결과를 대신하지도 않는다.

### 28.3 화면 검사

자동 검사는 다음을 확인한다.

- 세 질환 모두 공개 시험 15개를 검색 대상으로 사용한다.
- 질환이 같은 시험 5개만 후보로 남긴다.
- 핵심 합성 답 5개는 확인 행동 전에 환자 상태에 들어가지 않는다.
- 환자 상태, 검색, 조건 불러오기, 조건 판단, 정보 확인, 최종 결과의 여섯 단계가
  모두 표시된다.
- 합성 답을 적용하기 전에 Enter를 기다릴 수 있다.
- 역할별 호출 수와 토큰, 결과 파일과 단계별 기록 위치를 표시한다.

## 29. 새 환자·시험 파일을 받는 일반 실행 명령

### 29.1 연결한 입력과 출력

`run-screening`은 저장소의 환자 ID를 고르는 대신 다음 파일을 직접 받는다.

- 환자 사실과 선택적인 이동·비용·시간 부담을 담은 JSON
- 임상시험과 조건을 담은 JSON, JSONL 또는 JSON 배열
- 선택적인 답변 JSON

답변 파일을 주지 않으면 터미널에서 질문한다. 한 줄 답변, JSON 답변과 `@파일경로`를
받을 수 있고, `unknown`은 현재 답을 모른다는 뜻으로 처리한다. `quit` 또는 `save`로
끝내면 현재까지의 질문, 공개된 사실과 실행 횟수를 `session.json`에 저장한다. 다음
실행에서 이 파일을 `--resume`으로 주면 이미 확인한 내용을 다시 묻지 않는다.

예제 환자 한 명과 시험 세 건을 외부 모델 없이 실행했을 때 시험 세 건을 읽고 두 건을
후보로 남겼다. 한 번의 답을 반영한 뒤 두 후보의 확인을 끝냈다. 모델 역할과 같은
합성 환자를 만들 때 저장한 답만 반환하는 실험용 코드는 처음 조건 판단, 다음 확인
문장 작성, 관련 조건 재판정에 각각 한 번씩 사용됐다. 종료 뒤 이어서 실행하는 검사도
같은 최종 결과를 냈다.
Windows의 기존 한국어 코드페이지에서도 화면 글자가 깨지지 않도록 CLI 입출력을
UTF-8로 맞추고 실제 터미널 출력을 다시 확인했다.

### 29.2 범용성의 경계

일반 명령은 환자 수치나 시험 조건을 코드 안에 고정하지 않는다. 다만 입력 필드와
조건 연산자는 공개 JSON 규격을 따라야 한다. 자유롭게 작성된 진료기록을 자동으로
이 규격으로 바꾸는 기능은 별도 선택 명령이다.

## 30. 반복 호출 축소

기존 통합 화면은 매 주기마다 진행 관리 모델을 부르고 시험별 조건 판단도 따로
호출했다. 새 기본 실행은 안전한 다음 단계가 하나면 코드가 바로 진행하고, 같은 시점에
바뀐 모든 시험 조건을 한 요청에 묶는다. 비교를 위해 예전 방식도 설정으로 남겼다.

`natural-type_2_diabetes-11` 한 명을 GPT-5.6 Sol `medium`으로 다시 연결한 결과는
다음과 같다.

| 실행 | 전체 모델 호출 | 제공자 보고 토큰 |
|---|---:|---:|
| 기존 통합 화면 | 22회 | 321,910 |
| 진행 관리 모델을 생략하고 여러 시험 조건을 한 요청에 묶은 방식 | 8회 | 129,463 |

호출 수는 약 64%, 토큰은 약 60% 줄었다. 두 실행은 같은 기본 환자와 확인 한도 3회를

사용량을 확인한 결과이므로 정확도 향상을 뜻하지 않는다.

## 31. 전체 흐름 일괄 평가와 자동 보고서

### 31.1 세 방식 비교

새 `run-workflow-evaluation` 명령은 다음 세 방식을 같은 합성 환자에 실행한다.

1. 추가 정보를 확인하지 않고 처음 환자 자료만 사용
2. 처음 빠진 정보 목록에 적힌 순서대로 최대 세 개를 확인
3. 남은 세 번 안에 가장 많은 시험 판단을 끝낼 정보를 매번 다시 계산

세 방식 모두 같은 여러 시험 실행기, 조건 집계와 답변 환경을 사용한다. 환자별 실행은
병렬로 처리할 수 있지만 한 환자 안의 질문과 재판정 순서는 그대로 유지한다. 외부 모델
없이 30명을 실행한 결과는 다음과 같다.

| 전체 프로그램에서 부족한 정보를 처리한 방법 | 모든 환자 정보를 알 때와 같은 판단에 도달한 시험 비율 | 후보를 계속 볼지 제외할지 같은 결론을 낸 비율 | 환자 한 명당 실제로 확인한 정보 수 |
|---|---:|---:|---:|
| 추가 정보를 확인하지 않고 처음 환자 자료만 사용 | 42% | 100% | 0.00개 |
| 처음 빠진 정보 목록에 적힌 순서대로 최대 세 개를 확인 | 66% | 100% | 2.27개 |
| 남은 세 번 안에 가장 많은 시험 판단을 끝낼 정보를 매번 다시 계산 | 77% | 100% | 2.93개 |

가장 많은 시험 판단을 끝낼 정보를 매번 계산한 방법은 입력 목록 순서대로 확인한
방법보다 환자 16명에서 좋고 12명에서 같았으며 2명에서 낮았다.
이 평가는 검색, 조건 판단, 질문, 답변과 재판정을 실제 실행기에 모두 연결했다. 질문
정책 계산만 따로 실행한 75.3%와 88.7%보다 더 많은 경로 규칙을 검사하므로 두 결과를
같은 통계로 합치지 않는다.

실제 구독 연결은 한 환자와 세 방법에서 오류 없이 끝났다. 추가 정보를 확인하지 않은
경우, 입력 목록 순서대로 확인한 경우, 가장 많은 시험 판단을 끝낼 정보를 매번 계산한
경우는 각각 2회, 8회, 8회 호출했고 38,718토큰, 129,683토큰, 129,463토큰을 사용했다.
이 결과는 대규모 성능 수치가 아니라 실제 모델 연결과 비용 규모 확인이다.

### 31.2 자동 보고서

`build-report`는 질문 정책, 환자 부담, 전체 흐름과 후보 검색 결과 JSON을 읽어 다음
파일을 만든다.

- 핵심 수치를 모은 `summary.json`
- 표 계산에 바로 쓸 `metrics.csv`
- 보고서 문장과 표를 담은 `report.md`
- 질문 정책과 환자 부담을 그린 SVG

그림과 표의 숫자는 코드에 복사해 넣지 않고 입력 결과 파일에서 읽는다. 모든 부담
상황을 합쳤을 때 모든 환자 정보를 알 때와 같은 판단에 도달한 시험 비율은 84.0%에서
79.2%로 낮아졌다. 반면 이동·비용 제한 때문에 사용할 수 없는 확인 방법을 제외한
상황에서는 81.0%에서 88.5%로 높아졌고, 어려운 새 검사·추가 방문을 선택한 횟수는
65회에서 0회가 됐다. 자동 보고서는 이 상충 관계를 함께 표시한다.

범용 실행, 중단·재개, 세 방식 평가, 병렬 실행, 토큰 집계와 보고서 생성까지 포함한
이 시점의 전체 자동 검사 249개가 통과했다.

## 32. 보고서에서 실험 맥락이 빠진 표현 정리

처음 자동 보고서는 비교 방법과 측정값을 짧은 내부 이름으로만 표시해, 실험 전체를
이미 알아야 뜻을 짐작할 수 있었다. 다음처럼 고쳤다.

- 비교 방법 이름에 처음 자료, 확인 순서와 최대 확인 횟수를 함께 표시
- 결과 비율에 “모든 환자 정보를 알 때의 판단과 같아진 시험”이라는 비교 대상을 표시
- 환자 부담 결과에 이동·비용 제한과 새 검사·추가 방문 조건을 표시
- 전체 프로그램 표의 역할 실행 횟수와 토큰 0의 이유를 바로 아래에 설명
- TREC 내부 파일 이름 대신 연도와 공개 임상시험 검색 평가자료라는 뜻을 표시

보고서 생성기, README, 보고서·발표 정리본과 세 개의 SVG를 같은 표현으로 맞췄다.
자동 검사에서는 보고서 본문에 `no_questions`, `fixed_order`, `trec_2021` 같은 내부
식별자가 노출되지 않고, 비교 대상과 측정 의미가 포함되는지 확인한다.

## 33. 일반 실행의 입력 근거·실패·승인·검색 경로 보강

직접 입력 화면에서 공식 결과를 요청했다는 이유만으로 답을 공식 확인 자료로 저장하던
기본값을 없앴다. 문장 입력은 환자가 말한 내용, 확인 전 상태와 날짜 미상으로 저장한다.
공식 결과로 쓰려면 JSON에 자료 종류, 자료 위치, 확인 상태와 실제 날짜가 들어와야
한다. 실행 기록에는 문장, 직접 JSON, JSON 파일 중 어떤 방식으로 받은 자료인지와
각 항목을 입력자가 직접 밝혔는지도 남긴다.

`unknown` 답이 나오면 해당 정보는 이번 실행에서 얻지 못한 항목으로 저장한다. 그
정보만 반복하지 않고 다른 부족 정보를 계속 확인한다. 이후 자료가 생기면 사용자가
`--retry-unavailable`을 붙여 다시 시도할 수 있다. 새 검사처럼 환자 선택과 담당자
승인이 모두 필요한 방법은 두 상태를 따로 저장하며, 둘 다 기록되기 전에는 도구가
실행되지 않는다.

일반 실행의 후보 검색기에도 TrialGPT BM25·MedCPT 어댑터를 연결했다. 수만 건에서
찾아온 후보 중 사용자가 준 시험 파일에 구조화 조건이 있는 시험만 조건 판단으로
넘긴다. 첫 후보 목록과 검색 방법은 세션에 저장해 재개 실행에서 그대로 사용한다.

자동 보고서의 전체 흐름 표에는 다음 값을 추가했다.

- 후보 유지·제외를 맞힌 비율
- 현재 자료로 참가 조건을 확정할 수 있는지 맞힌 비율
- 남겨야 할 시험을 잘못 제외한 수
- 정보가 부족한데 확정한 수
- 질문 뒤 판단 대기에서 최종 판단으로 바뀐 시험 수
- 같은 환자에서 두 질문 순서를 비교한 승·동률·패

이 변경의 자동 검사는 직접 입력 출처 구분, 정보를 얻지 못한 뒤 다른 질문 진행,
명시적 재시도, 환자 선택과 담당자 승인 뒤 재개, 외부 검색 순위 연결과 보고서 지표
출력을 다룬다. 전체 자동 검사 256개가 통과했다. 외부 모델은 호출하지 않았으며 모델
성능 수치는 새로 만들지 않았다.

## 34. 대회 합성 환자 입력과 설명 가능한 추천 순위 연결

팀이 전달한 합성 환자 파일은 환자 열 개를 `topics` 배열에 넣고, 각 항목의 `num`에는
환자 번호, `title`에는 환자 기록 문장을 넣은 형식이다. 실제 제공 파일을 그대로 읽어
열 개 항목과 첫 환자 문장을 확인했다. `title`은 구조화된 환자 상태가 아니므로
`run-challenge`가 문장에서 질환과 환자 사실을 먼저 정리한 뒤 기존 전체 실행기에 넘긴다.

변환 결과는 다음 파일로 남긴다.

- 원래 환자 문장과 문장에서 찾은 사실을 함께 적은 `prepared-input.json`
- 기존 범용 실행기가 그대로 읽는 `prepared-patient.json`
- 후보 시험의 정리된 조건을 담은 `prepared-trials.json`
- 질문과 답변을 이어서 실행할 `session.json`
- 최종 판단·추천 순위·모델 사용량을 담은 `result.json`

처음 검색 순위는 조건 판단과 세션 재개까지 보존한다. 최종 목록은 현재 자료로 조건
확인이 끝난 시험을 먼저 놓고, 추가 정보가 필요한 시험은 남은 정보가 적은 순서로
놓는다. 같은 상태에서는 처음 검색 순위를 따른다. 각 시험에는 최종 목록 순위, 처음
검색 순위와 순서를 정한 이유가 함께 저장된다. 질문 답변으로 판정 상태가 바뀌면 목록도
같은 규칙으로 다시 만들어진다.

외부 모델 없이 실행한 통합 검사에서는 합성 환자 문장 한 건을 읽어 환자 사실을 만들고,
시험을 검색하고, 조건을 판단해 최종 추천 1위와 처음 검색 1위를 결과 파일에 저장했다.
추가 정보가 없는 완결 사례도 실행할 수 있도록 기존 질문 목록의 불필요한 최소 개수
제약을 없앴다. 전체 자동 검사 262개가 통과했다. 이번 작업에서는 외부 모델을 호출하지
않았으므로 원문 구조화 정확도나 추천 성능 수치는 새로 주장하지 않는다.

## 35. 임상시험 조건 정리본 재사용

`run-challenge`는 처음 읽은 임상시험의 정리된 조건과 부족 정보 정의를
`runs/trial-protocol-cache`에 저장한다. 같은 시험 원문, 같은 조건 정리 지시문과 같은
모델 설정으로 다시 실행하면 저장본을 읽고 조건 정리 모델을 호출하지 않는다.

합성 시험 한 건을 같은 설정으로 두 번 실행한 자동 검사에서 첫 실행은 환자 기록 정리,
시험 조건 정리, 조건 판단을 각각 한 번 호출해 총 3회였다. 두 번째 실행은 시험 조건
정리 호출을 생략해 총 2회였고, 최종 판단과 추천 순위는 같았다. 시험 원문의 숫자를
7.0에서 8.0으로 바꾸거나 모델 이름을 바꾸면 저장본을 사용하지 않고 새로 정리했다.

저장 경로, 재사용한 시험 수, 새로 정리한 시험 수, 손상된 파일 수와 저장 실패 수는
결과와 세션에 남긴다. 캐시를 읽거나 쓰지 못해도 본 실행은 중단하지 않는다. 전체 자동
검사 265개가 통과했다. 저장된 조건 내용을 임의로 바꾼 검사에서도 이를 사용하지 않고
원문에서 다시 정리했다. 외부 모델은 호출하지 않았으므로 실제 비용 절감량은 아직
측정하지 않았다.

## 36. 대회 입력 실행 코드 분리

기존 `challenge.py`는 topics 입력 형식, 환자 문장 변환, 결과 파일 저장, 캐시와 전체
실행 순서를 한 파일에서 처리했다. `cli.py`에도 같은 명령의 옵션 정의와 모델 연결이
들어 있어 수정할 위치를 찾기 어려웠다.

동작을 바꾸지 않고 다음 네 부분으로 나눴다.

- 입력과 실행 옵션을 검사하는 계약
- 환자 문장을 공통 입력으로 바꾸고 파일로 저장하는 변환
- 캐시·검색·판정·질문·세션을 연결하는 실행 관리
- 명령줄 옵션과 모델 제공자를 준비하는 CLI 처리

기존 `clarifytrial.app.challenge` import는 얇은 연결 파일로 유지했다. 기존 명령 옵션과
도움말, topics 입력 변환, 조건 캐시 재사용, 최종 추천 결과를 다시 검사했고 전체 자동
검사 265개가 통과했다. 외부 모델은 호출하지 않았고 판정 규칙과 결과 형식은 바꾸지
않았다.

## 37. GitHub 문서와 자동 보고서 정리

저장소 README는 핵심 아이디어, 전체 흐름, 자료, 현재 결과와 다음 평가 범위를 먼저
제시한다. 설치·실행·코드 위치는 마지막 개발자 참고 부분에 배치했다.

기존 현재 상태 문서의 요구사항 101개와 세부 구현 기록은
`CLARIFYTRIAL_IMPLEMENTATION_RECORD.md`로 보존했다. 새 현재 상태 문서는 완성된 범위,
핵심 결과, 다음 작업과 활성 요구사항만 설명한다. 다음 평가에서는 팀 공개 시험
1,931건을 넓은 검색 자료로 쓰고, 정밀 평가 범위를 약 10개 질환·50개 시험으로
확장하기로 한 결정을 연구계획, 데이터 문서와 출처 문서에 함께 기록했다.

질문 결과는 사람이 결과의 의미를 바로 알 수 있도록 세 번 안에 판단을 끝낸 시험 수로
표현했다. 전체 연결 평가의 63개, 99개, 115개를 README, 발표 정리본과 결과 그림에
같게 사용했다. 자동 보고서 생성기의 `모든 환자 정보를 알 때와 같은 판단` 표현도
`미리 정한 시험 상태에 도달해 판단을 끝냄`으로 바꿨다.

검사 결과는 다음과 같다.

- Markdown 파일 48개에서 깨진 로컬 링크 0개
- 전체 자동 검사 265개 통과
- `run-challenge`와 `build-report` 도움말의 문서 명령 일치 확인
- 질문 순서와 환자 부담 SVG를 다시 생성하고 1,200픽셀 화면에서 글자 겹침 없음 확인
- `git diff --check` 오류 없음

외부 모델과 의료 API는 호출하지 않았으며 연구 결과 수치는 새로 계산하지 않았다.

## 38. 팀 공유 문구 정리

연구 요약, README, 자료 구성과 자동 보고서에서 문서의 용도나 독자의 행동을 설명하는
문장을 제거했다. 연구 사실, 확인된 결과와 결과 범위를 직접 서술하도록 통일했다.

자동 보고서 첫 문단도 문서 소개 대신 평가 대상과 수치 출처를 바로 표시한다. 저장된
평가 결과로 보고서를 다시 생성해 새 문구를 확인했고, 전체 자동 검사 265개와 Markdown
파일 48개의 내부 링크 검사가 통과했다. 외부 모델과 의료 API는 호출하지 않았다.
