## 1. 결정된 구조

ClarifyTrial은 임상시험 조건을 미리 정리하고, 날짜와 출처가 붙은 환자 상태표를
만든 뒤, 후보 검색부터 조건 판단과 다음 확인까지 한 흐름으로 처리한다.

핵심 결과는 두 가지다.

| 질문 | 결과 |
|---|---|
| 이 환자를 후보로 계속 검토할 것인가? | 후보 유지 / 후보 제거 / 판단 어려움 |
| 현재 자료로 참가 조건을 확인할 수 있는가? | 현재 확인 / 확인 대기 / 부적합 / 판단 어려움 |

확인 대기 상태에서는 판정을 억지로 끝내지 않는다. 결과를 바꿀 수 있는 부족 정보
하나를 고르고, 그 정보를 기존 기록, 환자 답변, 공식 검사·의료진 확인 중 어디에서
얻을지 정한다.

## 3. 단계별 설계

### 3.1 임상시험 조건 준비

임상시험 원문은 프로토콜 버전마다 한 번 정리한다.

- 선정 조건과 제외 조건
- 수치, 단위와 비교 방법
- 요구 기간과 판단 기준일
- AND, OR, 부정과 예외
- 환자 답변으로 확인 가능한지 여부
- 기존 기록이나 공식 확인이 필요한지 여부
- 원문 위치

LLM이 조건을 나눈 뒤 코드가 수치, 날짜, 단위와 논리 구조를 확인한다. 원문과
구조화 결과가 맞지 않는 항목은 검토 대상으로 남긴다. 이 단계는 TrialMatchAI와
EXACT의 조건 구조화를 참고한다.

### 3.2 환자 상태표

여러 기록에서 같은 환자 정보를 반복해서 해석하면 단계마다 값이 달라질 수 있다.
따라서 모든 단계가 같은 상태표를 읽는다.

| 저장 항목 | 예시 |
|---|---|
| 환자 사실 | 절대 호중구 수 1,700/µL |
| 원문 위치 | 합성 기록의 문장 ID |
| 자료 종류 | 검사 결과, 진료 기록, 환자 답변, 공식 확인 |
| 사건 날짜 | 검사가 시행된 날짜 |
| 기록 날짜 | 문서가 작성된 날짜 |
| 확인 상태 | 원문에 직접 있음 / 추정 / 충돌 / 확인 대기 |

검색용 요약과 동의어는 후보 검색에만 쓴다. 환자 상태를 새로 확정하는 근거에는
원문과 연결된 사실만 사용한다. 상태표 구조는 PRomop에서 가져왔다.

### 3.3 후보 시험 검색

검색은 다음 순서로 진행한다.

1. 모집 상태, 나이, 성별과 지역처럼 명확한 값으로 1차 확인
2. BM25로 글자가 직접 겹치는 시험 검색
3. MedCPT로 뜻이 가까운 시험 검색
4. 두 검색 순위 결합
5. 후보 시험 안에서 환자와 관련 있는 조건을 위로 재정렬

후보 검색 단계는 놓치는 시험을 줄이는 데 초점을 둔다. 조건을 판단할 때는 검색용
요약 대신 시험 원문을 사용한다. TrialMatchAI와 TrialGPT의 검색 구조를 따른다.

### 3.4 조건별 판단

선정 조건과 제외 조건을 따로 처리한다.

| 조건 종류 | 상태 |
|---|---|
| 선정 조건 | 충족 / 불충족 / 자료 부족 / 해당 없음 |
| 제외 조건 | 위반 / 위반하지 않음 / 자료 부족 / 해당 없음 |

각 결과에는 환자 근거 ID, 시험 조건 ID, 판단 이유와 부족 정보 ID가 붙는다. 한
모델 호출에서 한 후보 시험의 관련 조건을 묶어 처리해 호출 수와 문맥 차이를 줄인다.

### 3.5 근거 확인

조건 판단이 끝나면 다음 항목을 확인한다.

- 판단과 설명이 서로 맞는가
- 환자 기록에 없는 사실을 덧붙였는가
- 시험 원문의 수치, 기간, 부정과 예외를 지켰는가
- 판단 기준일 뒤의 정보를 사용했는가
- 서로 연결된 조건을 따로 보아 의미가 달라졌는가

날짜, 수치, 단위와 명확한 논리는 코드가 매번 확인한다. LLM 근거 검토는 최종 결과
직전에 한 번 실행하고, 문제가 발견된 조건만 다시 판단한다. 이 단계는 TRIAGE의
자동 검토 구조를 작게 옮긴 것이다.

### 3.6 두 판단

#### 후보 유지

- `retain`: 참가 가능성이 남아 있고 추가 확인 가치가 있음
- `remove`: 되돌리기 어려운 명확한 제외 근거가 있음
- `uncertain`: 환자 근거 또는 시험 조건이 서로 충돌함

#### 현재 확인

- `confirmed`: 현재 단계에서 요구하는 근거가 충분함
- `not_confirmed`: 가능성은 있으나 날짜·출처·절차 확인이 남음
- `ineligible`: 명확한 조건 위반 근거가 있음
- `uncertain`: 자료가 있어도 의학적 해석이나 조건 뜻이 모호함

예를 들어 3개월 전 혈액검사가 정상이라면 후보 유지에는 도움이 된다. 시험에서
최근 14일 이내 결과를 요구할 경우 현재 상태는 `not_confirmed`로 두고 새 결과를
기다린다.

### 3.7 지금 더 확인할지 결정

현재 정보로 중요한 후보의 두 판단을 끝낼 수 있는지 먼저 본다. 결론이 충분하면
추가 질문을 만들지 않는다. 정보가 부족하면 결과를 바꿀 수 있는 사실만 후보로
올린다. MediQ의 정보 충분성 판단을 이 위치에 사용한다.

### 3.8 다음 정보와 확인 경로 선택

다음 확인은 아래 순서로 고른다.

1. 명확한 제외나 현재 확인 상태를 바꿀 가능성
2. 해결되는 중요한 조건과 후보 시험의 수
3. 답을 얻을 경로의 신뢰도
4. 환자 부담, 위험, 대기 시간과 비용
5. 잘못된 답으로 유력 후보를 제거할 위험

첫 구현은 위 순서를 그대로 적용한다. 숫자 가중치는 정답 자료가 생긴 뒤 별도
실험에서 조정한다. 여러 후보에 공통으로 필요한 정보를 먼저 보는 기준은 DQueST,
비용과 영향 범위를 함께 보는 기준은 Fink 계열에서 가져왔다.

| 행동 | 선택하는 상황 |
|---|---|
| `LOOKUP_RECORD` | 이미 존재할 가능성이 높은 검사 결과, 치료일, 진료 기록 |
| `ASK_PATIENT` | 환자가 직접 알고 답할 수 있는 복용, 과거 수술, 생활 정보 |
| `REQUEST_VERIFICATION` | 공식 검사 결과, 수행 상태, 의료진 판단이 필요한 정보 |
| `DEFER` | 현재 안전하게 확인할 경로가 없거나 사람의 해석이 필요한 경우 |
| `NONE` | 추가 확인이 현재 결과를 바꾸지 않는 경우 |

환자 질문은 `ASK_PATIENT`가 선택된 경우에만 만든다. 검사값을 환자 기억에 맡기거나
시스템이 검사를 자동 주문하는 흐름은 사용하지 않는다.

### 3.9 새 정보 반영과 종료

합성 평가 환경이 미리 정한 답을 반환한다.

- 기록 조회: 합성 EHR에서 해당 사실 반환
- 환자 질문: 환자가 직접 알 수 있는 숨은 사실 카드에서 반환
- 공식 확인: 미리 정한 결과와 이용 가능 시점 반환

새 정보에는 출처와 사건 날짜를 붙인다. 그 정보와 연결된 조건만 다시 판단하고,
바뀐 이유를 실행 기록에 남긴다.

다음 중 하나에 해당하면 흐름을 끝낸다.

- 중요한 후보의 현재 상태가 결정됨
- 남은 정보가 결과를 바꾸지 않음
- 허용된 확인 경로가 없음
- 행동 한도에 도달함
- 사람 검토가 필요한 조건이 남음
- 환자가 현재 후보를 확인하고 중단함

## 4. 실제 실행 단위

반복 계산은 코드에 맡기고, 의미 판단이 필요한 부분에만 LLM을 사용한다. 하나의
역할이 언제나 하나의 API 호출을 뜻하지는 않는다.

| 실행 단위 | 방법 | 실행 시점 | 결과 |
|---|---|---|---|
| 시험 조건 정리 | LLM + 코드 검사 | 프로토콜 버전마다 한 번 | 구조화 조건과 원문 위치 |
| 환자 사실 정리 | LLM + 코드 정규화 | 새 비정형 기록이 들어올 때 | 날짜·출처가 붙은 환자 상태표 |
| 후보 검색 | 코드 | 초기 검색과 검색 조건 변경 시 | 후보 시험과 관련 조건 |
| 조건 판단 | LLM | 초기 판단과 관련 사실 변경 시 | 조건 상태와 근거 ID |
| 날짜·수치 검사 | 코드 | 조건 판단마다 | 규칙 위반 표시 |
| 근거 검토 | LLM | 최종 출력 직전 | 수정할 조건 또는 승인 |
| 두 판단 집계 | 코드 | 조건 결과 변경 시 | 후보 유지와 현재 확인 |
| 정보 충분성·다음 행동 | LLM + 허용 규칙 | 결과가 아직 열려 있을 때 | 부족 사실과 확인 경로 |
| 합성 답변 환경 | 코드 | 행동 실행 시 | 미리 정한 새 사실 |
| 결과 보고 | 코드 템플릿 | 종료 시 | 근거, 남은 정보와 면책 문구 |

첫 버전에는 역할 간 토론을 넣지 않는다. 날짜·수치 검사와 원문 근거 확인으로 먼저
오류를 줄이고, 반복 검토는 실제 오답 유형과 정답이 확보된 뒤 비교한다.

## 5. 모델과 실행 조건

| 용도 | 모델 | 설정 |
|---|---|---|
| 주 비교 | Claude Sonnet 5 | `medium` effort, 상황에 따라 생각량 조절 |
| 성능 상한 확인 | Claude Opus 4.8 | `high` effort, 대표 사례만 실행 |
| 저비용 작동 확인 | Solar Pro 4 | 제공자가 지원하는 중간 추론 설정 |

모든 주 비교는 같은 Sonnet 5 설정을 사용한다. 사례에 따라 모델을 바꾸는 자동
전환은 사용하지 않는다. 모델 제공자별 차이는 공통 어댑터가 처리하며, 에이전트
코드와 평가기는 그대로 둔다.

Sonnet 5는 비기본 `temperature`, `top_p`, `top_k` 값을 받지 않는다. 샘플링 값은
API 기본값을 사용하고, 같은 지시문과 구조화 출력 형식을 고정한다. LLM을 쓰는
평가는 사례마다 세 번 실행해 평균과 결과가 달라진 사례 비율을 함께 기록한다.

## 6. 호출 규칙과 출력 형식

시험 조건과 환자 상태표는 공통으로 미리 계산해 구조 비교에 제공한다. 한 환자
흐름의 최대치는 다음과 같다.

- 외부 확인 행동 최대 3회
- 모델 호출 최대 12회
- JSON 형식 수정 최대 1회
- 근거 검토 뒤 조건 재판정 최대 1회

12회는 초기 조건 판단, 행동 선택, 최대 세 번의 새 정보 반영, 최종 근거 검토와
형식 수정까지 포함한 상한이다. 실제 호출 수, 토큰, 시간과 비용을 별도 결과로
남긴다.

모든 시스템의 결과는 다음 공통 형식으로 바꾼다.

```text
조건별 상태와 환자·시험 근거 ID
후보 유지: retain / remove / uncertain
현재 확인: confirmed / not_confirmed / ineligible / uncertain
다음 행동: LOOKUP_RECORD / ASK_PATIENT / REQUEST_VERIFICATION / DEFER / NONE
확인하려는 사실 ID와 조건 ID
종료 이유
```

형식 오류, 시간 초과와 빈 결과는 각각 오류로 기록한다. 평가 정답으로 모델 출력을
채우지 않는다.

## 7. 선행연구와 구조의 연결

| 구조 | 참고한 연구 | 가져온 부분 |
|---|---|---|
| 환자 상태표 | PRomop | 여러 기록에서 현재 상태를 한 번 계산해 공유 |
| 조건 준비 | TrialMatchAI, EXACT | 기준을 계산 가능한 항목으로 나누고 원문 위치 보존 |
| 검색과 조건 판단 | TrialMatchAI, TrialGPT | 규칙 필터, 글자·의미 검색, 재정렬, 조건별 근거 |
| 대화와 후보 갱신 | CLEAR-MATCH, Yang | 답변마다 후보와 대화 목적 갱신 |
| 근거 검토 | TRIAGE | 판정, 환자 원문, 시험 원문과 기준일 대조 |
| 정보 충분성 판단 | MediQ | 답할지 더 확인할지 먼저 결정 |
| 다음 정보 우선순위 | DQueST, Fink | 여러 후보에 미치는 영향과 확인 비용 고려 |
| 두 판단과 확인 경로 | ClarifyTrial v5 | 후보 유지와 현재 확인을 분리하고 허용 행동 선택 |

EXACT는 구조화 규칙이 많은 좁은 질환에서 TrialMatchAI식 LLM 판정을 바꿔 끼우는
대안이다. Yang의 연구는 가장 가까운 전체 대화형 비교 대상으로 사용한다. 공개된
세부가 부족한 부분은 공통 환경에서 재구성한 구조 비교로 표시한다.

## 8. 구현 순서

1. **공통 자료형**
   - 시험, 조건, 환자 사실, 두 판단, 다섯 행동과 근거 ID
2. **작은 RAG**
   - 조건 저장소, BM25 검색과 원문 위치 반환
3. **공통 평가기**
   - 숨은 합성 상태, 행동 결과, 조건·두 판단·다음 행동 채점
4. **고정 후보 조건 판단**
   - TrialGPT 1,015건 변환기, 단일 모델, TrialGPT식 구조
5. **대화와 행동 정책**
   - 모두 확인, CLEAR-MATCH식, DQueST식, Fink식, MediQ식
6. **ClarifyTrial v5**
   - 환자 상태표, 두 판단, 확인 경로, 선택적 재판정과 근거 검토
7. **넓은 검색과 공식 코드**
   - TREC 전체 검색, TrialMatchAI와 EXACT 연결

## 9. 비교 실험

첫 구조 비교에는 다음 시스템을 넣는다.

1. 강한 단일 모델의 한 번 판단
2. 기존 여섯 단계 흐름을 Sonnet 5로 다시 실행한 비교군
3. 모든 부족 정보를 정해진 순서로 확인하는 단순 정책
4. TrialGPT식 조건별 판단
5. CLEAR-MATCH식 대화와 후보 갱신
6. DQueST식 영향 후보 수 우선 정책
7. Fink식 영향 범위와 부담 우선 정책
8. MediQ식 정보 충분성 판단
9. ClarifyTrial v5 전체 구조

같은 환자, 후보 시험, 검색 결과, 모델, 행동 한도와 합성 답변 환경을 사용한다.
과거 Solar 실행값은 가져오지 않고 구조만 같은 조건에서 다시 실행한다.

결과는 다음 항목으로 나눠 본다.

- 후보 검색 회수율과 순위
- 조건 상태와 근거 선택 정확도
- 유지해야 할 후보를 너무 일찍 제거한 비율
- 확인이 남았는데 참가 조건을 확정한 비율
- 알맞은 확인 경로 선택률
- 질문·조회·공식 확인 수
- 모델 호출, 토큰, 시간과 비용

## 10. 현재 주장 범위

지금 확정된 내용은 구조와 실험 방법이다. v5 코드는 아직 없고 성능도 측정하지
않았다. TrialMatchAI, CLEAR-MATCH, EXACT보다 정확하다는 주장, 질문 수와 검토
시간이 줄었다는 주장, 실제 임상 업무에 사용할 수 있다는 주장은 실험 뒤에 판단한다.

ClarifyTrial은 같은 환자 사실에서 후보를 남기는 판단과 현재 자료로 조건을
확인하는 판단을 분리한다. 연구는 이 구분이 성급한 후보 제거와 너무 이른 확정을
줄이는지 측정하는 데 초점을 둔다.
